# Pipeline Validation Harness (+ Mock Pipeline Service)

A mock async pipeline service plus a batch validation harness that exercises it.

## Layout

```
mock_service/        FastAPI mock pipeline (POST /jobs, GET /jobs/{id}, GET /jobs?input_type=)
  app.py             API routes
  db.py              SQLAlchemy models / Postgres session
  processing.py       deterministic "true" output generation + fault injection
  worker.py           in-process async worker pool (queued -> processing -> completed/failed)

harness/              the batch validation harness (the main deliverable)
  compare.py           tolerance-based comparison logic (pure, unit-testable)
  runner.py            submit batch -> poll concurrently -> compare -> report
  run.py               CLI entrypoint
  fixtures/golden.json example golden/expected fixtures

tests/                 pytest suite (job lifecycle, async e2e, comparison unit tests)
docker-compose.yml      Postgres for local dev
requirements.txt
```

## Running it

```bash
# 1. Postgres
docker compose up -d
# (or point DATABASE_URL at any Postgres instance)

pip install -r requirements.txt

# 2. Start the mock service
export DATABASE_URL="postgresql+psycopg2://postgres:postgres@localhost:5432/pipeline_test"
python3 -m uvicorn mock_service.app:app --port 8000

# 3. Run the harness against it
python3 -m harness.run --base-url http://localhost:8000 --fixtures harness/fixtures/golden.json
# exits 1 if any case failed (CI-friendly)

# 4. Run the test suite (uses the same Postgres, a separate in-process app instance)
python3 -m pytest
```

## Architecture & flow

1. `POST /jobs` inserts a `queued` row and hands the job id to an in-process
   worker queue.
2. A small pool of background threads (`worker.py`) pulls job ids, flips the
   row to `processing`, calls the mock pipeline (`processing.run_pipeline`,
   which sleeps to simulate work), then writes `completed`/`failed` + output.
3. `GET /jobs/{id}` just reads the row — the caller is responsible for polling.
4. The harness submits the whole batch first (in parallel), then polls all
   jobs concurrently, to mirror real pipeline concurrency rather than
   serializing what's actually async work.
5. Each result is compared to a golden fixture with `compare.py`, which walks
   nested dicts/lists and uses combined relative+absolute tolerance for
   numbers (exact match for strings/bools).

## Tool choices & why

- **FastAPI + SQLAlchemy + Postgres**: matches the assignment's explicit ask
  ("persisted in Postgres"). FastAPI gives free request validation/typed
  responses, which keeps the mock's contract honest.
- **In-process thread pool for "async" workers**, instead of Celery/RQ/SQS:
  a real queueing system would be infrastructure we'd just have to fake
  anyway for a take-home. Threads give genuine concurrency and out-of-order
  completion (real async-pipeline behavior) without extra moving parts.
- **JSONB output column**: the structured output's exact shape is pipeline-
  specific and may evolve; JSONB avoids a migration every time a new metric
  is added, at the cost of weaker DB-level schema enforcement (acceptable
  here — validation is the harness's job, not Postgres's).
- **requests + ThreadPoolExecutor in the harness** rather than asyncio: the
  harness is I/O-bound but small-scale (batches, not millions of jobs);
  threads keep the code readable without async/await ceremony. Would switch
  to `httpx.AsyncClient` if batch sizes grew into the thousands.
- **TestClient (in-process ASGI) for the test suite** instead of spinning up
  a live uvicorn subprocess: avoids host/port flakiness in CI while still
  exercising the real app, real Postgres, and real worker threads.

## Tradeoffs / things a production system would do differently

- A real worker pool would run in separate processes/containers reading from
  a durable queue, so a process crash doesn't lose in-flight jobs (the
  current in-memory queue does on restart).
- No retry/backoff logic for failed jobs — out of scope for a mock, but a
  real harness would likely want to distinguish "transient infra failure"
  from "pipeline produced a wrong answer" as different alert severities.
- Golden fixtures here are generated by calling the mock's own "true value"
  function (see `harness/fixtures/generate_golden.py`). That's a shortcut
  unique to building both sides of this exercise — a real harness's golden
  values would come from an independent, trusted oracle, not the system
  under test.

## Test reliability (order/repetition)

- Every test function truncates the `jobs` table first (`tests/conftest.py`),
  so no test depends on another's leftover rows.
- The one true end-to-end async test (`test_async_lifecycle.py`) uses a
  `fault_overrides` hook on job creation to force deterministic success/
  failure, rather than relying on the mock's randomized ~5–10% fault rates,
  which would otherwise make that specific test flaky.
- Verified via `pytest-randomly` (randomizes test order) across multiple
  consecutive runs — all 25 tests pass every time.

## Assumptions

- The assignment's API contract is taken literally: `POST /jobs` returns
  only `{job_id, status}`; `GET /jobs/{id}` returns `{job_id, status,
  input_type, output}`. Error detail is tracked internally (`error` column)
  for debugging but isn't part of the public contract.
- "Numeric fields by tolerance" is implemented as combined relative+absolute
  tolerance per field, configurable per test case (`rel_tol`/`abs_tol`), with
  exact-match fallback for non-numeric fields and an `ignore_fields` escape
  hatch for legitimately-variable fields like version strings.
